## 1. Executive Summary

**Overall health grade: B+.** This is an unusually well-kept small production service: 893 test
functions across four apps, current dependencies (Django 6.0.6), a real CI gate (lint, format,
types, tests, Sonar), documented backups with retention, invite-only registration, a deliberate
security posture (CSP, peppered Argon2id, django-axes, nh3 sanitization, SSRF allowlists), and a
CLAUDE.md that mostly matches reality. What keeps it from an A: a handful of genuine correctness
defects that tests structurally cannot catch (a static-manifest case-mismatch that likely 500s the
event detail page in production, an apparently unauthenticated upload endpoint, image uploads that
crash on non-RGB color modes), a data-churn hazard in the scraper import pipeline, and a pattern of
small documentation/config contradictions (docs claim a PBKDF2 fallback hasher that settings don't
configure). None of these require architectural change; all are fixable in days.

**Top 3 risks**
1. `DEFAULT_EVENT_IMAGE = "images/logo.PNG"` doesn't match `static/images/logo.png` on disk — under
   production's strict manifest storage this raises on the event detail page for any imageless
   user-submitted event (`events/models.py:35`).
2. `markdownx.urls` is mounted without authentication (`config/urls.py:65`) — django-markdownx's
   upload endpoint is anonymous by default, allowing unauthenticated image uploads into R2.
3. A partially-broken scraper deletes every event it fails to re-find (`base_import.py:295-310`),
   and recreated events get new UUIDs/slugs — breaking shared links and duplicating entries in
   subscribers' calendars (iCal UID = event UUID, `events/feeds.py:57`).

**Top 3 opportunities**
1. A production-parity static/storage smoke test in CI would have caught risk #1 and prevents the
   whole class (tests currently swap in non-manifest storage, `conftest.py:16-24`).
2. A "sanity threshold" guard in the importer's stale-deletion path is ~20 lines and removes the
   biggest data-integrity hazard.
3. Consolidating the four copies of owner-check / event-limit / pending-image logic in
   `events/views.py` would shrink the file ~20% and make the next feature cheaper.

## 2. Repository Map

**Purpose.** Community calendar for Copenhagen dance/performance events: public browsing, feeds
(iCal/RSS), invite-only publishing, plus a scraper pipeline that imports events from 8 venue
websites nightly.

**Tech stack.** Django 6.0 on Python 3.14, PostgreSQL (SQLite in dev), server-rendered templates +
HTMX (no JS framework), Tailwind 4 via npm CLI, `uv` for Python deps, Cloudflare R2 for media,
Railway for hosting (web + 2 cron services), Resend for email, Sentry for errors, WhiteNoise for
static files. Type-checked with `ty`, linted with ruff (incl. bandit `S` rules).

**Architecture sketch.**

```
                    ┌──────────────────────────────────────────────┐
 Browser ── HTMX ──▶ config/ (settings, CSP middleware, ratelimit) │
                    │   ├─ events/    CRUD views, feeds, map, SEO  │──▶ PostgreSQL
                    │   └─ accounts/  claim-code auth, profiles    │──▶ R2 (images)
                    └──────────────────────────────────────────────┘
 Railway scrape-cron ─▶ run_scrapers ─▶ scrapers/<source>.py ─▶ JSON ─▶ import_events
                                        (registry.py wires scrape fn ↔ import config)
 Railway backup-cron ─▶ scripts/backup_db.py ─▶ pg_dump → gzip → R2 (30-day retention)
```

**Key directories**

| Path | Role |
|---|---|
| `config/` | Settings, root URLs, CSP middleware, cache-based rate limiting, PWA endpoints |
| `accounts/` | Custom UUID/email User, ClaimCode invite flow, peppered Argon2 hasher, zxcvbn validator |
| `events/` | Event model + CRUD/list/map views, iCal/RSS feeds, image pipeline, Nominatim geocoding, JSON-LD/sitemaps |
| `scrapers/` | 8 per-venue scrapers + `registry.py` (single source of pipeline config) + shared HTTP utils |
| `events/management/commands/` | `base_import.py` upsert engine, `run_scrapers.py` orchestrator, digest/backfill |
| `templates/`, `static/` | Global templates, vendored HTMX/Leaflet, PWA assets |
| `scripts/backup_db.py` | Standalone DB backup cron |
| `.claude/` | Session hooks: dependency setup on start, pre-commit gate before PR creation |

**Depth of review.** The web layer (`config/`, `accounts/`, `events/` minus templates), the import
pipeline, and all operational config received a close read. The 8 scraper modules (~3,300 lines of
site-specific HTML parsing) and the HTML templates/JS received a lighter structural review — they
are leaf code with dedicated fixture tests and no security surface beyond what `base_import.py`
already mediates. Admin customizations (`accounts/admin.py`) were skimmed.

**Surprises (mostly good).**
- The rate limiter's docstring documents a subtle DatabaseCache `incr()` TTL bug and the
  window-bucketing that sidesteps it (`config/ratelimit.py:34-48`) — rare care for a hobby-scale app.
- `registry.py` makes adding/retiring a scraper a one-place change, including per-source SSRF image
  domain allowlists and category-scoped stale deletion for sources sharing an `external_source`.
- Boot-time guards refuse to start production with the dev SECRET_KEY (`config/settings.py:17-28`)
  or a missing/short PASSWORD_PEPPER (`accounts/hashers.py:38-57`).
- Less good: the same thoroughness produced contradictions — docs describe behavior (hasher
  fallback, field limits) that the code no longer has.

## 3. Audit Report

Severity scale: **Critical** = active exploitation/data-loss path; **High** = user-visible breakage
or security weakness reachable today; **Medium** = real defect, bounded blast radius; **Low** =
hygiene.

### 3.1 Security

**S1 — HIGH. Unauthenticated markdownx endpoints mounted.**
[Fact] `config/urls.py:65` includes `markdownx.urls` with no auth wrapper; nothing in the repo
overrides the views (only `robots.txt` disallows the path, `config/urls.py:34`). django-markdownx
4.0.11 (locked in `uv.lock`) ships its `ImageUploadView` and `MarkdownifyView` without a login
requirement. [Judgment, verify against the installed package] Consequence: any anonymous visitor
with a CSRF cookie can POST images (≤4 MB each, `config/settings.py:377-378`) into R2 storage —
cost/abuse vector and free image hosting under pleskal's domain — and burn CPU on the markdown
preview endpoint. The widget is used for event descriptions and bios (`events/forms.py:58`,
`accounts/forms.py:28`), so the endpoint is needed — but only for logged-in users.

**S2 — MEDIUM. Email change bypasses mandatory verification.**
[Fact] `ProfileForm` exposes `email` (`accounts/forms.py:23`) and nothing syncs allauth's
`EmailAddress` on change (grep: `EmailAddress` is only touched at registration
`accounts/views.py:263`, login check `:108`, and admin). The login gate only blocks users with an
*unverified* record — after an email change the old *verified* record still passes. Consequence:
`ACCOUNT_EMAIL_VERIFICATION = "mandatory"` (`config/settings.py:263`) holds only for the first
address; a user can switch login/password-reset to any unowned address, and the EmailAddress table
silently diverges from `User.email` (admin's "resend verification" acts on stale rows).

**S3 — MEDIUM. Image-download allowlist can be bypassed via redirects.**
[Fact] `_download_image` uses `urllib.request.urlopen`, which follows redirects
(`events/management/commands/base_import.py:82-87`), while the domain allowlist is checked only
against the original URL (`base_import.py:341-357`). [Judgment] A compromised or misconfigured
venue site could redirect the cron container to internal endpoints or giant files. Blast radius is
small (runs only in the scrape cron against 8 trusted sites, response is Pillow-validated), hence
Medium, not High.

**S4 — MEDIUM (documentation/config contradiction with security implications).**
[Fact] `accounts/hashers.py:13-16` and CLAUDE.md both state PBKDF2 is kept as a fallback hasher and
legacy hashes auto-migrate on login. `config/settings.py:129-131` lists **only**
`HmacPepperedArgon2PasswordHasher`. Consequence: if any pre-migration PBKDF2 hash still exists in
production, that user cannot log in (Django raises "unknown algorithm" on verify); if none exist,
the docs are simply wrong. Cannot be verified from the repo — needs a production query (see Open
Questions).

**S5 — LOW. Feed hit counters are an unauthenticated DB write.**
[Fact] Every GET of `/feed/events.ics` or `.rss` performs `FeedHit.record()` — an
`update_or_create` write (`events/feeds.py:85,123`; `events/models.py:259-270`) — and neither feed
is rate-limited. [Judgment] At current traffic this is noise; it's just the only unauthenticated
write amplification on the site.

**Otherwise healthy.** No hardcoded secrets (checked settings, workflows, scrapers; CI uses
obviously-fake values, `.github/workflows/ci.yml:33-37`). XSS handling is disciplined: nh3 allowlist
(`events/templatetags/markdown_filters.py:8-30`), hand-escaped JSON-LD
(`events/structured_data.py:16,82-85`), URL-scheme validation (`events/validators.py:39-48`). CSP is
tight and real (`config/middleware.py:43-56`). Session/CSRF cookie flags, HSTS, SSL redirect all set
(`config/settings.py:319-329`). Uploads are Pillow-validated, EXIF-stripped by re-encode, and
capped. Rate limiting covers the right endpoints. Dependencies are current (Django 6.0.6, allauth
65.18, axes 8.3.1 in `uv.lock`); no known-CVE pins spotted.

### 3.2 Code Quality & Correctness

**Q1 — HIGH. `DEFAULT_EVENT_IMAGE` case mismatch breaks event detail in production.**
[Fact] `events/models.py:35` reads `DEFAULT_EVENT_IMAGE = "images/logo.PNG"`, but the file on disk
is `static/images/logo.png` (lowercase; only `logo-white-bg.PNG` is uppercase). Production uses
WhiteNoise's `CompressedManifestStaticFilesStorage` (`config/settings.py:180`), whose manifest
lookup is case-sensitive and strict — `static("images/logo.PNG")` raises `ValueError` for a missing
manifest entry. `display_image_url` falls through to this default for every event with no image and
no publisher default — i.e. all user-submitted events without an uploaded image
(`events/models.py:157-167`) — and the detail view calls it unconditionally for the og:image tag
(`events/views.py:521-523`). [Judgment] Expected symptom: HTTP 500 on those detail pages in
production only. Tests can't catch it because the autouse fixture swaps in non-manifest storage
(`conftest.py:16-24`). Flagged as needing a 1-line prod/staging repro since this sandbox can't run
the app; the mechanism (case-sensitive dict lookup + `manifest_strict`) is not in doubt.

**Q2 — MEDIUM. Uploaded images in unsupported color modes crash with a 500.**
[Fact] `validate_and_process` converts only `RGBA`/`P` modes (`events/images.py:27-28`); the
`img.save(..., format="WEBP")` call at `events/images.py:36` is outside the try/except, and the
callers catch only `ValidationError` (`events/views.py:57-65`). Pillow's WebP encoder rejects modes
like CMYK (common in print-origin JPEGs), raising `OSError`. Consequence: a valid JPEG in CMYK mode
turns into an unhandled 500 instead of a form error. Also [Judgment]: flattening RGBA to RGB without
compositing on a background renders transparent regions black.

**Q3 — MEDIUM. Failed-submission images are stashed hex-encoded in the DB session.**
[Fact] On any invalid create/update form with an image attached, the raw upload (≤10 MB) is stored
hex-encoded (2× size) in `request.session["pending_image"]`
(`events/views.py:176-183`, `:553-561`), which in production is a database-backed session row.
It is only removed on a subsequent successful save (`:195`, `:578`). Consequences: up to ~20 MB
written into `django_session` per failed submit; Django then loads that session on **every
subsequent request** by that user until it's popped, and abandoned drafts leave the blob until
session expiry (1 week, `config/settings.py:327`). [Judgment] Clever UX, wrong storage tier.

**Q4 — MEDIUM. Importer deletes real events on partial scraper failure, and re-creates them with new identities.**
[Fact] Stale deletion removes every DB event absent from the incoming JSON
(`events/management/commands/base_import.py:295-310`). `run_scrapers` only skips import when a
scraper returns **zero** events (`events/management/commands/run_scrapers.py:142-146`). iCal UID is
the event UUID (`events/feeds.py:57`) and slugs are regenerated on re-create
(`events/models.py:109-118`). Consequence: a venue redesign that lets a scraper find 5 of 40 events
silently deletes 35; the next good run restores them as *new* rows — shared URLs 404 in the interim
and forever after (new slug), and calendar subscribers get duplicate entries (new UIDs). Recent
history shows this is not hypothetical: two of the last ten commits are "Fix HAUT scraper missing
events" (`git log`: `a4b5688`, `50ef0b9`).

**Q5 — LOW. Slug generation can exceed the column on collision.**
[Fact] `_generate_unique_slug` truncates the base to `MAX_TITLE_LENGTH` (250 — the *title*
constant), then appends `-<4 hex>` (`events/models.py:109-118`); `slug` is `max_length=250`
(`:53`). A colliding ≥246-char slug produces a 255-char value → `DataError` on Postgres. Edge case,
but it's a crash where a truncation was intended.

**Q6 — LOW. Duplicated logic across event views.**
[Fact] Owner checks exist twice (`EventOwnerMixin`, `events/views.py:125-135` vs.
`EventDuplicateView._check_owner`, `:622-626`); the upcoming-event-limit block is duplicated
verbatim (`:148-167` vs. `:628-646`); the pending-image save/restore block appears twice
(`:174-197` vs. `:552-587`); `EventDuplicateView.post` renders the same error context three times
(`:693-726`). [Judgment] `events/views.py` (773 lines) is the complexity hotspot of the web layer;
each copy has already drifted slightly (the update path adds a `hasattr(image_file, "read")` guard
the create path lacks, `:584`).

**Q7 — LOW. Dead and contradictory validation code.**
[Fact] `events/validators.py:13-36` (`validate_image_file`, with a format allowlist) is referenced
only by tests — the real pipeline uses `events/images.py`, which enforces no format allowlist.
[Fact] `ProfileForm.clean_bio` validates >2000 chars but its error text and help text say "1,500"
(`accounts/forms.py:43,55-58`). [Fact] Form caps description at 2000 (`events/forms.py:100`) while
the model allows 4000 (`events/models.py:55`).

### 3.3 Architecture & Design

[Judgment] The architecture is right-sized and boundaries are mostly clean: `scrapers/` knows
nothing about Django; `registry.py` is the single wiring point; `config/ratelimit.py` is a proper
reusable mixin; feeds/sharing/structured-data are small focused modules. No circular imports
observed; the lazy imports sprinkled through views (`events/views.py:83,99,116`) are signal-safety
habit, not cycle workarounds — a few are unnecessary noise.

**A1 — MEDIUM. Synchronous geocoding in the request path with 2 sync workers.**
[Fact] `Event.save()` calls Nominatim inline (`events/models.py:186-237`); the client enforces a
1.1 s inter-request gap and a 5 s timeout (`events/geocoding.py:33-34,44-51`); gunicorn runs 2 sync
workers (`Dockerfile` CMD). Consequence: an uncached venue on event submit holds a worker up to
~6.6 s; two concurrent submits can occupy both workers. The cache mitigates this for repeat venues
(and the module docstring is honest about the trade-off). [Fact] The rate-limit lock is
per-process, so 2 web workers + the cron can collectively exceed Nominatim's 1 req/s policy.
[Judgment] Acceptable for now; worth a queue/deferral only if submission volume grows.

**A2 — LOW. Every listing query filters/sorts on unindexed columns.**
[Fact] `Event` declares no indexes beyond PK/slug/unique-constraint (`events/models.py:48-99`);
every public query filters `start_datetime` + `is_draft` and sorts by `start_datetime`
(`events/views.py:238-241`, `events/feeds.py:30-33`). [Judgment] Irrelevant at hundreds of rows;
a single composite index is a cheap future-proofing win.

### 3.4 Testing

[Fact] 893 test functions across `accounts/`, `events/`, `config/`, `scrapers/`; per-scraper
fixture tests; dedicated security tests (`accounts/tests/test_security.py`,
`test_ratelimit.py`, `test_hashers.py`). CI enforces `--cov-fail-under=80` on Postgres 16 with
branch coverage (`.github/workflows/ci.yml:72`). Could not be executed in this sandbox (Python
3.14 download blocked); the suite is the same one the repo's pre-PR hook runs, and SonarCloud
badges are wired.

**T1 — MEDIUM. Tests are structurally blind to production storage behavior.**
[Fact] The autouse fixture replaces both storages with simple backends (`conftest.py:16-24`),
which is exactly why Q1 survived. There is no test that runs `collectstatic` with the manifest
backend and resolves every statically-referenced asset.

**T2 — LOW. Coverage config excludes `config/*`** (`pyproject.toml:78`) — the rate limiter and CSP
middleware are tested (`accounts/tests/test_ratelimit.py`, `config/tests/test_pwa.py`) but their
lines don't count, understating/overstating nothing today, yet a regression in `config/ratelimit.py`
coverage would be invisible.

[Judgment] Test *quality* sampled well: view tests assert behavior (status codes, DB effects,
redirects), not just 200s; hasher tests cover wrong-pepper failure modes. No flaky patterns spotted
(no sleeps except in scraper politeness delays, which tests stub).

### 3.5 Performance

Healthy for its scale. List/map views use `select_related("submitted_by")`
(`events/views.py:241`); counts are two cheap queries; the map view materializes upcoming events
once. The real items are already listed: Q3 (session bloat — also a per-request performance tax),
A1 (blocking geocode), A2 (indexes), S5 (feed write per hit). One more:

**P1 — LOW. Image downloads happen inside the import DB transaction.**
[Fact] `_maybe_update_image` (network, up to 20 s timeout per image,
`base_import.py:86,262,285`) runs inside the per-event `transaction.atomic()` blocks, which
themselves sit inside one outer transaction spanning the whole import (`:200`). [Judgment] Long
transactions on a small Postgres are tolerable at 8 sources but this is the first thing to hurt as
sources grow.

### 3.6 Dependencies

Healthy. `uv.lock` present and current (Django 6.0.6, pillow 12.2, sentry-sdk 2.62, requests
2.34.2); Dependabot implied by CI's dependabot guard (`ci.yml:75`). Two nits:
[Fact] `pytest-xdist` sits in production dependencies (`pyproject.toml:20`) — test tooling shipped
in the deploy image. [Fact] `requires-python = ">=3.14"` (`pyproject.toml:6`) while ruff targets

### 3.7 Developer Experience & Operations

Strong: one-command setup via `uv sync` + session-start hook, pre-commit runs the full gate
including pytest, `railway.toml` preDeploy runs migrations + cache table, `/health/` endpoint,
Sentry release tagging from git tags, backups with retention and a documented restore path

**D1 — LOW.** [Fact] The weekly digest cron exists only as a manual Railway setup instruction
(`deployment-notes.md:145-152`) — unlike scrape/backup crons there is no `railway.*.toml` for it,

**D2 — LOW.** [Fact] Root logging is WARNING-and-up to console only (`config/settings.py:347-371`);
scraper INFO lines rely on `logging.basicConfig` inside the command (`run_scrapers.py:73`).
[Judgment] Fine for Railway log tails; just know there is no request-level logging.

### 3.8 Documentation

CLAUDE.md is exceptional in breadth and mostly accurate, which makes its drift points worth fixing
precisely because people (and agents) trust it:
[Fact] claims title max 200 chars — actual 250 (`events/models.py:17`); claims PBKDF2 auto-migration
(see S4); the CSP middleware docstring says `script-src 'self'` while the code adds the Ko-fi host

### 3.9 Strengths (what to preserve)

  fail fast beats silently-insecure.
- **Registry-driven scraper pipeline** (`scrapers/registry.py`) with per-source SSRF allowlists and

- **Documented non-obvious decisions in code**: the rate-limit window bucketing rationale

- **Test discipline**: 893 tests, factories, per-scraper fixtures, security-specific test modules.
- **Privacy-aware defaults**: feeds never expose submitter identity (`events/feeds.py:113`),

- **Ops story**: backups + retention + restore docs, Sentry release tagging, health checks, PWA

## 4. Improvement Strategy

### Theme 1 — Close the gap between test reality and production reality
Most of the serious findings (Q1, and the reason S4 is unverifiable) share one cause: production
behaviors (manifest static storage, real hasher config, real storage backends) are swapped out in
tests. **Target state:** CI contains a small "production-parity" job: `collectstatic` with the
WhiteNoise manifest backend, then resolve every static path referenced from Python and templates;
plus a check that every `PASSWORD_HASHERS`-relevant claim has a test. **Principle:** every autouse
test override is a documented blind spot with a compensating CI check.

### Theme 2 — Make the importer preserve identity and fail safe
Q4 + Q5 + P1: the import pipeline treats events as disposable rows, but URLs, slugs, and iCal UIDs
are public contracts. **Target state:** stale deletion refuses to run when the incoming set is
implausibly small vs. the DB set; matching key upgrades from delete+recreate churn tolerance to
identity stability (UID derived from `(external_source, source_url, start)` or events soft-hidden
rather than deleted); image downloads move outside DB transactions. **Principle:** scraped data is
untrusted input to a system whose outputs (URLs/UIDs) are commitments.

### Theme 3 — Every user input path either succeeds or fails as a form error
Q2, Q3, S1: uploads can 500, failure state is parked in the wrong tier, and one upload endpoint has
no auth. **Target state:** the image pipeline handles all Pillow modes (or rejects them with a
message), pending-image UX either re-prompts or uses temp file storage, markdownx endpoints require
login. **Principle:** anonymous users get read-only; authenticated mistakes get form errors, never
stack traces.

### Theme 4 — Docs as executable claims
S4 + 3.8: the repo's biggest cultural asset (CLAUDE.md precision) is decaying at the edges.
**Target state:** the contradictions are fixed once, and the two claims that matter (hasher
fallback, field limits) get trivial assertion tests so drift breaks CI. **Principle:** document
less if needed, but never wrongly.

### Explicitly *not* recommended now (trade-offs)
- **Async/queued geocoding (A1):** real flaw, wrong time. At current submission volume the cache
  absorbs it; a task queue adds an infra service to a $5-10/month budget. Revisit if event submits
  exceed ~dozens/day or Sentry shows worker starvation.
- **DB indexes (A2):** harmless to add, but with hundreds of rows it's ceremony. Bundle it with the
  next schema migration rather than deploying one for it.
- **Feed caching / rate limiting (S5):** wait for evidence in the weekly digest numbers.
- **Splitting `events/views.py` into modules:** dedupe within the file first (Q6); a package split
  at 773 lines is premature.
- **Redirect-hardening `_download_image` (S3):** legitimate, but the cron's threat model (8 trusted
  venue sites, Pillow re-encode, size implicitly bounded by memory) makes this M3, not M1.

### Definition of done (measurable)
- CI has a static-manifest resolution check; it fails if `DEFAULT_EVENT_IMAGE`-class bugs recur.
- `curl -F` an image to `/markdownx/upload/` unauthenticated returns 302/403, not 200.
- Importer run where a scraper returns <50% of that source's future events: zero deletions, one
  Sentry alert.
- A CMYK JPEG upload returns a form error page (200 with error), not a 500.
- `django_session` contains no `pending_image` payloads > 1 MB (or the feature stores files, not hex).
